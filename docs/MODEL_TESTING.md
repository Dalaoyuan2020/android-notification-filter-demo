# 模型与双路对照测试

适用于 **v0.2.0**。这版提供四种判断策略：默认关键词、官方模型、中转模型、双路对照。它提供可配置接口，**没有预填任何供应商、Base URL、模型 ID 或密钥**；用户提到的服务准确名称和地址仍待确认，尚未验证指定真实服务能够接通。

首次安装两个 APK、开启通知使用权和发送权限，请先看 [手机实测指南](PHONE_TESTING.md)。`rui460` 可先在 [仓库邀请页](https://github.com/Dalaoyuan2020/android-notification-filter-demo/invitations) 接受私有仓库邀请。修改源码和提交变更的方法见 [开发指南](../CONTRIBUTING.md)。

## 四种策略分别做什么

| 策略 | 处理方式 | 是否会清除通知 |
|---|---|---|
| 关键词 | 本机匹配已保存关键词；不请求模型 | 开启主界面“自动清除”后，按规则清除 |
| 官方模型 | 请求“官方配置”对应服务 | 先观察；单独开启“自动清除”后，才可能按模型结果清除 |
| 中转模型 | 请求“中转配置”对应服务 | 先观察；单独开启“自动清除”后，才可能按模型结果清除 |
| 双路对照 | 将同一条符合条件的通知分别交给两路，记录各自结果 | **始终只观察，不执行清除**；主界面自动开关不可用 |

“官方”“中转”是两份配置的路线名称，不代表 App 已认证服务商，也不是预装的供应商连接。中转可以连接由队友部署的自训模型，但需要服务端提供兼容接口；填写模型 ID 不会上传权重、训练模型或创建部署。

所有策略都先做本地保护：非目标来源、持续或不可清除通知、分组汇总、通话／导航／闹钟，以及命中保留词的通知不交给模型。模型策略下无可读正文也保留。**清除关键词只作用于关键词策略**；模型策略使用模型判断。

## 1. 先只用合成通知

1. 在主界面关闭 **“自动清除”**。
2. 把 **“目标 App 包名”**设置为 `com.example.notificationdemo.sender`，点击 **“保存规则”**。这样本轮只处理测试发送器，不把微博、微信或其他真实通知交给服务。
3. 点击 **“配置模型与双路对照”**。保持 **“允许远程处理目标通知”关闭**，先填写服务并做单路连接测试。

远程开关默认关闭。模型策略下远程关闭时，通知保留、不发送请求，也不会自动回退到关键词清除。开关和策略修改后都要保存才生效；已发送给服务的请求无法收回。

## 2. 填写两份配置

点击 **“编辑官方配置”**或 **“编辑中转配置”**，一次只显示一份表单，减少填错路线的机会。切换编辑按钮不会自动改变判断策略。

| 字段 | 如何填写 |
|---|---|
| 配置标签 / 版本标识 | 用于区分本轮实验，例如“基线 v1”“自训 checkpoint A”。不要填写密钥 |
| Base URL · HTTPS | 服务文档提供的兼容 API 基础地址；只支持 HTTPS，不含账号密码、查询参数和 URL 片段 |
| 模型 ID | 服务实际可调用的精确模型标识，包含必要的部署名或版本；不要猜测 |
| API Key | 服务提供的 Bearer 密钥；无需鉴权的自训端点可留空 |

手机中的 `localhost` 或 `127.0.0.1` 指向手机自身，不是开发电脑。自建服务需使用手机能访问的 HTTPS 地址和受信任证书；本 App 不放行明文 HTTP，也不跳过证书验证。不要把密钥拼进地址。

填完点击 **“保存配置并关闭自动清除”**。两份配置、策略和远程开关一起保存，**每次成功保存都会关闭主界面自动清除**。未保存内容在返回或旋转屏幕后会丢弃；API Key 使用密码框，并由本机密钥存储加密保存，不写入页面恢复状态、处理日志或仓库。卸载、清除数据或密钥存储失效后，需要重新配置。

## 3. 逐路测试连接

**“允许远程处理目标通知”控制真实通知的远程处理；单路连接测试是另一个显式操作。即使该开关关闭，点击连接测试仍会向当前配置的服务发送下方固定合成样本。** 它不读取通知栏。

先选择 **“编辑官方配置”**，保存后点击 **“仅测试当前配置（合成消息）”**；再选择 **“编辑中转配置”**，以同样方式测试第二路。表单有未保存修改时不会发请求，会提示先保存。每次只测试当前一路，不会同时请求两个服务。

固定样本为：

```text
包名：com.example.notificationdemo.synthetic
标题：连接测试：合成通知
正文：这是一条用于验证模型接口的合成通知，不包含真实用户消息。请保留此通知。
```

成功时页面展示返回判断、理由和本次请求耗时；合成样本预期应保留，如果模型建议清除也请如实记录。“测试成功”只说明本次接口响应符合客户端要求，不等于模型判断正确，也不代表通知读取、后台运行或自动清除已经通过。

失败时记录页面的安全错误提示、配置标签和模型 ID；不要把 API Key、完整原始服务响应或带凭据的地址贴进 Issue。离开页面后不会展示迟到的结果，已经发出的网络请求仍可能由服务端完成。

## 4. 接口兼容性需要验证

客户端按兼容的 Chat Completions 接口发送请求。服务名称相似、文档声称兼容或模型能在网页里聊天，都不能代替手机端实际验证。鉴权、地址路径、模型标识和返回结构必须与客户端支持的协议一致。

供接入服务的队友核对：

- 去掉 Base URL 末尾的 `/`，然后附加 `/chat/completions`；如果地址已以该路径结尾，则直接使用。**不会自动补 `/v1`**，服务需要时必须自行填入基础地址。
- 发送 HTTPS POST；有密钥时使用 `Authorization: Bearer …`。请求包含 `model`、`messages`（系统说明和通知 JSON）、`stream: false`、`response_format: {"type":"json_object"}`；未设置 temperature 或 token 数参数。
- 通知 JSON 包含 `package`、`title`、`text` 和 `category`。自训模型应把这些字段当作待判断数据，不能执行通知文本中的指令。
- 响应须为 `application/json`，`choices` 恰有一条，`finish_reason` 为 `stop`，消息角色为 `assistant`。不接受工具调用、拒绝消息或不完整生成。
- `message.content` 必须是严格 JSON 字符串，且只有 `action` 与 `reason` 两个字段：`action` 为大写 `KEEP` 或 `REMOVE`；`reason` 非空且不超过 240 字符，不含 Markdown 代码围栏。例如 `{"action":"KEEP","reason":"普通人际消息，建议保留"}`。
- 连接超时 6 秒、读取超时 8 秒，单请求总期限 15 秒；双路逐路请求，整条对照可能更久。通知字段总长度超过 12,000 字符时，直接保留，不截断发送；请求上限 64 KiB，响应上限 32 KiB。

固定合成测试样本的 `category` 为 `msg`。App 不自动跟随接口重定向，遇到重定向需确认后填写正确的最终 HTTPS 地址。

如果服务只提供其他协议，例如另一种生成接口、私有封装或自定义鉴权，请先由队友核对并适配客户端／中转服务。不要反复更换真实通知试探接口；使用固定合成连接测试即可判断基本兼容性。

## 5. 做双路对照

1. 两路固定合成连接测试分别成功后，选择 **“双路对照 · 只观察，不清除”**。
2. 阅读页面发送范围说明，开启 **“允许远程处理目标通知”**，点击 **“保存配置并关闭自动清除”**。
3. 返回主界面，检查当前策略是双路对照，处理方式为 **“对照观察”**，自动清除开关不可用。确认目标仍只有测试发送器。
4. 打开发送器，点击 **“清空本发送器的全部通知”**，再点击 **“发送一组验收样本 · 9 张”**。
5. 等待模型返回，再在筛选器 **“验证记录”**查找 **“模型对照”**记录，核对官方／中转的配置标签、模型 ID、耗时、判断理由和“两路结论一致／不同”。任一路失败时应显示无法比较，不应记为模型意见一致。
6. 点击发送器 **“刷新当前通知”**。对照模式下，原来的 **9 个对象都应保留**：

   ```text
   [101, 102, 103, 104, 105, 200, 201, 202, 203]
   ```

默认保留关键词和保护规则下，通常只有 101、102、201、202 四个样本进入模型；其余因重要词、空正文、持续通知或汇总保护而直接保留／跳过，所以不会为全部 9 张卡片都请求两路模型。通知栏可能折叠分组，以发送器的当前 ID 列表为准。

建议先比较“普通消息是否被误判为清除”“广告是否被识别”“失败率”“同样样本的耗时差异”。这批样本规模很小，只用于验证工作流程，不应据此宣布哪一个模型总体更准确。

## 6. 再测试单路自动处理

双路对照无法自动删除。若要验证模型清除流程，选择已验证的 **官方模型**或 **中转模型**，保持远程开启并保存。回主界面先确认观察结果，再手动开启 **“自动清除”**，清空发送器并重新发送样本。

模型判断不等于关键词规则，不能假设一定恰好清除 102、202。逐条记录实际结论和通知 ID，特别检查普通消息是否被误删。网络失败、超时、响应不符合协议或配置不可用时应保留；通知更新、策略修改或监听状态变化后，旧请求结果不应再删除新版本通知。

**“请求清除”不等于成功。** 需要同时核对“已清除”的系统确认记录，以及发送器当前 ID 列表。切换配置或修改规则时先关闭自动清除，避免把两次实验混在一起。

## 7. 停止与提交反馈

停止远程通知处理时，进入配置页关闭 **“允许远程处理目标通知”**并保存，或切回 **关键词**并保存。需要完全停止读取通知时，在系统中撤回筛选器的通知使用权。仅关闭主界面的“自动清除”只停止删除，不会停止模型观察请求。

到 [新建 Issue](https://github.com/Dalaoyuan2020/android-notification-filter-demo/issues/new/choose) 选择模型测试反馈表单，或查看仓库中的 [模型反馈表单定义](../.github/ISSUE_TEMPLATE/model-test.yml)。记录：

- Release、手机型号、Android／厂商系统版本。
- 策略、配置标签、模型 ID、目标包名和保留关键词；不提交 API Key。
- 两路固定合成测试是否成功；失败时的安全提示。
- 对照结果中的两路判断、耗时、差异，以及当前通知 ID。
- 普通后台、熄屏、重启后的连接情况；未测就写“未测试”。

只提交合成消息，截图遮盖地址中的内部信息和无关通知。即使仓库是私有的，也不要提交真实消息正文、联系人、验证码或任何凭据。
